**Audit and fix all wally-package-types subprocess calls in install.rs.**

Per RESEARCH.md scope audit, there are 4 wally-package-types call sites that ignore exit status — 2 in install_tools() and 2 in setup_wally_packages(). All should be treated as non-fatal warnings (wally-package-types failure means types aren't generated but packages are still installed).

**In install_tools() — verbose path (~line 77-83):**

Current code runs `.status()` but ignores the result. Change to:
```rust
let wpt_status = Command::new("wally-package-types")
    .arg("--sourcemap")
    .arg("sourcemap.json")
    .arg(pkg_dir)  // "Packages" or "ServerPackages"
    .status()
    .context("Failed to run wally-package-types")?;

if !wpt_status.success() {
    pb.suspend(|| output::warn(&format!(
        "wally-package-types failed for {} (types may be incomplete)",
        pkg_dir
    )));
}
```

Apply the same pattern to BOTH the Packages and ServerPackages calls in the verbose path.

**In install_tools() — capture path (~line 104-122):**

Current code runs `.output()` but ignores the result. Change to:
```rust
let wpt_out = Command::new("wally-package-types")
    .arg("--sourcemap")
    .arg("sourcemap.json")
    .arg(pkg_dir)
    .output()
    .context("Failed to run wally-package-types")?;

if !wpt_out.status.success() {
    pb.suspend(|| output::warn(&format!(
        "wally-package-types failed for {} (types may be incomplete)",
        pkg_dir
    )));
}
```

Apply to BOTH Packages and ServerPackages calls in the capture path.

**In setup_wally_packages() — verbose path (~line 216-221):**

Same pattern: capture .status() result and warn on failure:

```rust
    .arg(pkg_dir)

```

**In setup_wally_packages() — capture path (~line 222-228):**

Same pattern with .output():
```rust
let wpt_out = Command::new("wally-package-types")
    .arg("--sourcemap")
    .arg("sourcemap.json")
    .arg(pkg_dir)
    .output()
    .context("Failed to run wally-package-types")?;

        "wally-package-types failed for {} (types may be incomplete)",
        pkg_dir
```

**Key design decisions per CONTEXT.md:**
- wally-package-types failure is NON-FATAL (output::warn, not bail!) — packages are installed, only types are missing
- Do NOT use output::error_block() here — this is a degraded-but-functional state, not a command failure
- The existing spinner is active during these calls, so use `pb.suspend(|| ...)` for the warn message
- Exit code: these warnings do NOT cause install/setup-wally-packages to exit 1 — the overall command still succeeds

**Replace the serve stub in menu.rs run_command():**

Current stub code (the `"serve"` match arm ~line 166-172):
```rust
"serve" => {
    output::info(&format!(
        "serve is coming in a future update. Current version: {}",
        env!("CARGO_PKG_VERSION")
    ));
    Ok(())
}
```

Replace with the live dispatch that mirrors the main.rs Serve arm pattern:
```rust
"serve" => {
    let rt = tokio::runtime::Builder::new_multi_thread()
        .enable_all()
        .build()
        .context("failed to build tokio runtime")?;
    rt.block_on(crate::commands::serve::run(Some(cfg), None))
}
```

Note on ownership: `cfg` is used earlier in the function to extract `src` (via `cfg.paths.as_ref()`). The `"serve"` arm moves `cfg` into `Some(cfg)`. This is safe because:
- `src` is extracted as a `&str` from the borrowed `cfg.paths` before the match
- The match arm only executes ONE branch — so `cfg` is only moved in the serve path, not conflicting with `src` usage
- Verify that `src` extraction happens before the match statement (it does — line 116-121)

The `port` parameter is `None` because the interactive menu has no way to specify a port flag — it always uses the config/default port.

**Add tokio and anyhow::Context imports to menu.rs:**

The file currently imports `anyhow::Result` but NOT `anyhow::Context` (needed for `.context()` on the runtime builder). Add `Context` to the import:
```rust
use anyhow::{Context, Result};
```

tokio does not need a `use` import — it's referenced via full path `tokio::runtime::Builder::new_multi_thread()`.

**Update the format dispatch in menu.rs run_command():**

Plan 01 changed `format_code()` to accept a `check: bool` parameter. The menu format dispatch must be updated from:
```rust
"format" => crate::commands::quality::format_code(src),
```
to:
```rust
"format" => crate::commands::quality::format_code(src, false),
```

Menu dispatch always passes `check = false` — the interactive menu runs format in write mode. The `--check` flag is only available via CLI (`ezpm format --check`). This is correct by design per RESEARCH.md Pitfall 3.
