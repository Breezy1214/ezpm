  <name>Task 1: Create serve start-wait-kill integration test</name>
  <files>tests/serve_test.rs</files>
  <action>
**Create `tests/serve_test.rs`** with the serve start-wait-kill pattern:

- `mod common;` at the top
- Use `std::io::{BufRead, BufReader}`, `std::process::{Command, Stdio}`, `std::time::{Duration, Instant}`

**Test: `serve_starts_and_shuts_down`**:
1. Call `common::create_project()` for an isolated TempDir
2. Spawn `ezpm serve` using `Command::new(common::ezpm_bin())` with:
   - `.arg("serve")`
   - `.current_dir(dir.path())`
   - `.env("EZPM_NO_UPDATE_CHECK", "1")`
   - `.stdout(Stdio::piped())` — capture stdout for line scanning
   - `.stderr(Stdio::piped())` — capture stderr
   - `.spawn()` (not `.output()` — we need the child handle)
3. Take `child.stdout` and wrap in `BufReader`
4. Read lines with a 30-second deadline:
   - For each line, check if it contains `"Watching"` AND `"for changes"` (this is the ready indicator printed by `output::info()` after the 8-step startup — see serve.rs line 661)
   - If found, set a `ready` flag to true and break
   - If deadline exceeded, break
5. Assert `ready == true` with message "serve never became ready within 30 seconds"
6. Kill the child process with `child.kill()`
7. Wait for the child with `child.wait()`
8. The exit status after SIGKILL will be non-zero on Unix — that is expected and acceptable. The test passes because the ready line was observed, proving serve started correctly.

**Important considerations:**
- Serve invokes external tools (Rojo, DarkLua, etc.) that MUST be installed. If they are not, the test will fail at one of the 8 startup steps — this is correct behavior per the locked decision ("tests assume full toolchain is installed").
- Use a unique `--port` flag (e.g. `--port 44872`) to avoid conflict with any locally running Rojo on the default port 34872. This also avoids port collision if tests run in parallel (Pitfall 7).
- Keep TempDir alive through the entire test — do not drop it before `child.wait()` completes.

**Test: `serve_exits_nonzero_without_config`**:
1. Create a bare TempDir (no ezpm.toml, no project files)
2. Spawn `ezpm serve` in that directory using `common::run_ezpm(dir.path(), &["serve"])`
3. Assert failure — serve should fail because there is no project config

  <name>Task 2: Update CI workflow with rust-cache, Rokit, and ubuntu-only runner</name>
  <files>.github/workflows/ci.yml</files>
  <action>
**Replace the existing `.github/workflows/ci.yml`** with an updated workflow that:

1. **Triggers:** `push` to `main` AND `pull_request` targeting `main` (unchanged from current)
2. **Permissions:** `contents: read` (unchanged)
3. **Single `test` job on `ubuntu-latest`** (replaces the 3-platform matrix):
   - `actions/checkout@v4`
   - `dtolnay/rust-toolchain@stable`
   - `Swatinem/rust-cache@v2` — zero config required; caches `~/.cargo` and `./target` automatically
   - **Install Rokit step:** Download the latest Rokit Linux binary, install it, then run `rokit install` to get all tools from `rokit.toml` (StyLua, Selene, Rojo, DarkLua, Wally, wally-package-types, Lune). The install step should:
     ```
     curl -sSf https://raw.githubusercontent.com/rojo-rbx/rokit/main/scripts/install.sh | bash
     echo "$HOME/.rokit/bin" >> $GITHUB_PATH
     rokit install
     ```
     Note: The `scripts/install.sh` is the official Rokit install method. After install, `~/.rokit/bin` must be added to PATH so subsequent steps can find the tools. `rokit install` reads `rokit.toml` and installs all listed tools.
   - `cargo test` — runs both unit tests and all integration tests
   - `cargo clippy -- -D warnings` — warnings treated as errors
   - `cargo fmt --check` — verify formatting

4. **Separate `clippy` and `fmt` jobs are REMOVED** — consolidated into the single `test` job to reduce CI overhead. All three checks (test, clippy, fmt) run sequentially in one job. This is simpler and still achieves the sub-2-minute target since Swatinem/rust-cache eliminates most compilation time.

5. **Job name:** Use `test` (or `build-and-test` to maintain compatibility with any existing branch protection rules — check if branch protection is configured and use the same name). Per Pitfall 6 from RESEARCH.md, renaming jobs may require a CI run before the new names appear in GitHub's branch protection dropdown. Using a simple `test` name is fine since branch protection will be configured manually after the first run.

The workflow should look approximately like:

```yaml
name: CI

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

permissions:
  contents: read

jobs:
  test:
    name: Test
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: dtolnay/rust-toolchain@stable
        with:
          components: clippy, rustfmt
      - uses: Swatinem/rust-cache@v2
      - name: Install Rokit toolchain
        run: |
          curl -sSf https://raw.githubusercontent.com/rojo-rbx/rokit/main/scripts/install.sh | bash
          echo "$HOME/.rokit/bin" >> $GITHUB_PATH
      - name: Install project tools
        run: rokit install
      - name: Run tests
        run: cargo test
      - name: Clippy
        run: cargo clippy -- -D warnings
      - name: Format check
        run: cargo fmt --check
```
